What problem does it solve?

A customer says a webhook was delivered twice. The provider says both requests succeeded. The application team cannot tell whether the second request was a normal retry, a duplicate business action, or the same event ID reused with different content.

This tool gives support and integration engineers a controlled place to reproduce each condition. It verifies signatures before parsing, records delivery metadata and SHA-256 digests, and classifies every attempt without retaining the sensitive body.

Use cases

When to use it

Duplicate fulfillment

Send the same signed event twice and confirm that business work is claimed only once.

Signature failures

Compare a valid fixture with a corrupted signature or timestamp outside the replay window.

Event-ID collisions

Reuse an ID with changed content and prove that the receiver returns a conflict rather than treating it as a normal retry.

Ordering assumptions

Deliver fixtures out of order and test whether downstream code incorrectly assumes arrival order.

How it works

From signed request to safe evidence

  1. Create a fixture.

    The CLI builds a realistic event envelope with an ID, type, creation time, and body.

  2. Sign the exact bytes.

    An HMAC signature and timestamp are attached before the request is sent.

  3. Verify before parsing.

    The receiver rejects invalid or stale requests before JSON parsing or persistence.

  4. Claim the event atomically.

    SQLite distinguishes a first delivery, same-body duplicate, and changed-body ID collision.

  5. Inspect the ledger.

    Outcomes, timestamps, event IDs, and digests remain available; payload_body: not retained.

Worked example

“The invoice was fulfilled twice”

First, start the receiver. Then send one payment event twice with the same ID and body.

Reproduce the retry

webhooklab serve --port 8080

# in another terminal
webhooklab chaos payment.succeeded \
  --duplicate

Expected attempts

{"http_status":202,
 "outcome":"processed"}

{"http_status":202,
 "outcome":"duplicate"}

What this proves

The receiver acknowledges both delivery attempts but creates one event claim. If the same ID arrives with a different digest, the result changes to 409 id_collision. Support can now tell engineering whether the problem is receiver idempotency, provider retry behaviour, or invalid event reuse.

Evidence

What the ledger keeps

Kept: event ID, type, attempt time, outcome, HTTP result, and SHA-256 digest.

Not kept: payload body, signing secret, Authorization values, or customer data.

{
  "delivery_attempts": 2,
  "unique_events": 1,
  "duplicate_rate": 0.5,
  "outcomes": [
    {"outcome": "processed", "count": 1},
    {"outcome": "duplicate", "count": 1}
  ]
}
Architecture

A deliberately small receiver

Fixture CLI→HMAC signature→FastAPI receiver→Atomic event claim→SQLite ledger

The CLI is responsible for fixtures and failure recipes. The receiver owns verification and classification. The store uses one transaction so concurrent deliveries cannot both become the first claim.

Get started

Run the debugger

git clone https://github.com/Emmanuelasika/webhook-delivery-debugger.git
cd webhook-delivery-debugger
python -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
webhooklab serve --port 8080

The installed command remains webhooklab for compatibility. Open http://127.0.0.1:8080 for the delivery ledger.

What it is not

This is a local reliability and reproduction tool, not a hosted webhook gateway. It does not queue production deliveries, retry customer traffic, or replace provider logs. Production use would need authentication, multi-tenancy, encrypted secrets, retention policy, rate controls, and durable backups.
